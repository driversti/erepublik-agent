# Work Overtime — Daily-runner integration

**Status**: design approved
**Date**: 2026-05-20
**Author**: Yurii Chekhotskyi
**Related code**: `src/agent/runner.ts`, `src/agent/actions.ts`, `src/agent/cycle.ts`, `src/memory/schema.ts`, `src/tools/work.ts`, `src/ui/*`
**Reference KB**: `~/Projects/erepublik/kb/Work_Overtime.md`, `~/KnowledgeBase/Erepublik/API/economy/work.md`, `~/KnowledgeBase/Erepublik/Daily_Challenge.md` (mission `100002`)

## Goal

Add a deterministic `workOvertime` capability to the daily runner: read `/en/main/job-data`, gate on documented preconditions (points ≥ 24, energy ≥ 10, cooldown elapsed) plus the player-practice employer per-day cap, and POST `/en/economy/workOvertime`. Support two operator-selectable modes via `config/settings.json`:

- **`once-per-day`** — fire one overtime per PST day; satisfies mission `100002` and banks one salary.
- **`when-available`** — fire whenever the API allows; used by players with stockpiled points (thousands) who want to grind multiple overtimes per day.

## Background

Overtime is a secondary work action at the same employer that pays only in the employer's local currency (CC). Mechanics summary (full notes: `kb/Work_Overtime.md`):

| Aspect | Value / behaviour |
|---|---|
| Status endpoint | `GET /en/main/job-data` → `{ overTime: { points, nextOverTime, salary, usableEnergy } }` |
| Action endpoint | `POST /en/economy/workOvertime` with form `action_type=workOvertime&_token={csrf}` |
| Points requirement | `overTime.points ≥ 24` |
| Energy requirement | `overTime.usableEnergy ≥ 10` |
| Cooldown | 60 min; `nextOverTime` is Unix-seconds when next OT is allowed (`0` = available) |
| **Anti-spam trap** | POSTing while `nextOverTime > now` still **succeeds** but **burns 100 energy instead of 10**. MUST be avoided. |
| Reward | Local currency (CC). The `xp:2` / `health:100` fields in responses are trivial side effects — not weighed in priority decisions. |
| Mission tie-in | Mission `100002` ("Work as employee 2 times") — completed by regular `work` + 1 OT. |
| Points source | Owning buildings + 1 per Daily Objectives chest claimed. Not generated by fighting/training. |
| Employer per-day cap | Server-side cap set by the employer. No pre-flight API signal — manifests as a `status: false` POST response when all client-checkable preconditions are clean. |

## Requirements

**R1**: Read `job-data` and POST `workOvertime` only when:
  - `overTime.points ≥ 24`
  - `overTime.usableEnergy ≥ 10`
  - `overTime.nextOverTime === 0 || overTime.nextOverTime ≤ now`

**R2**: Cycle ordering (within the safe-daily action loop):

```
work → train → workOvertime → vipClaim → buyFood
```

OT must run **after** regular `work` (mission `100002` only completes when both are done) and **after** `train` (cheap, fast, no shared dependency). OT runs **before** the farm gate so the 10-energy cost is paid before fuel pacing.

**R3**: Mode selector in settings:

- `workOvertime.enabled: boolean` (default `true` — feature ships on by default)
- `workOvertime.mode: 'once-per-day' | 'when-available'` (default `'once-per-day'`)

**R4**: Employer per-day cap — when the agent POSTs `workOvertime` with all client-checkable preconditions satisfied (points, energy, cooldown clear) and receives a `status: false` response, set `state.overtimeCapReachedAt = now()` and stop trying OT for the rest of the eRepublik day. The flag clears automatically at day rollover (it lives in `DailyState`).

**R5**: External-completion reconciliation — at the start of every cycle, after fetching `job-data`, if `overTime.nextOverTime > now` (cooldown active) and `state.completedActions.workOvertime` is unset, mark it `{ at: now, source: 'external' }`. This treats an in-cooldown read as "someone (player / another bot) did OT recently".

  *Caveat:* the cooldown timer is also the agent's own footprint immediately after a successful POST. The reconcile MUST run **before** the OT action this cycle (so we don't accidentally mark our own pending POST as external), and the OT action mutates the flag itself on success.

**R6**: Telegram notifications:
  - **Success**: `💼 OT: +{netSalary} {currency}` (one message per successful POST)
  - **Cap reached** (first time per day): `⛔ overtime: employer cap reached — paused until day rollover`
  - **Cooldown / preconditions** → silent (high frequency, no operator action needed). Logged to console only.

**R7**: UI dashboard:
  - Add `workOvertime` flag to `dailyActions` row (alongside Work / Train / VIP / Food).
  - Add a settings card with `enabled` toggle and `mode` selector.

**R8**: Digest — extend `formatDigest` to include OT status: `Work ✅ Train ✅ OT ✅ VIP ✅ Food ✅`.

## Non-goals

- **No `useEnergyBar=yes`.** Energy bars are valuable; never auto-consume them on OT. (The endpoint accepts this flag — we explicitly omit it.)
- **No multi-attempt loop per cycle.** Even in `when-available` mode, run at most one POST per cycle. The 10-min cycle period naturally limits throughput; the next cycle handles the next attempt.
- **No proactive cooldown wait.** If cooldown is active, skip this cycle. We do not block the cycle waiting for the cooldown to elapse.
- **No proactive switching jobs.** If the cap is hit, we don't auto-resign or hunt for a higher-cap employer. The operator handles employer choice manually.
- **No detection of mission 100002 completion as an OT signal.** The mission completes on regular `work` + 1 OT, so its "completed" state doesn't uniquely identify OT being done. `job-data.nextOverTime` is the canonical signal.

## API anchor

### `GET /en/main/job-data` — slim response shape we care about

```json
{
  "isEmployee": true,
  "alreadyWorked": true,
  "overTime": {
    "points": 10342,
    "nextOverTime": 1769331700,
    "salary": 15000,
    "usableEnergy": 8308
  }
}
```

Existing allowlist does **not** include `/en/main/job-data` (the only existing reader is `jobMarket.ts` which uses `/en/economy/job-market-json/...`). Allowlist entry required.

### `POST /en/economy/workOvertime` — success

```json
{
  "status": true,
  "message": true,
  "result": {
    "netSalary": 7425,
    "grossSalary": 7500,
    "tax": 75,
    "currency": "LTL",
    "days_in_a_row": 3764,
    "xp": 2,
    "health": 100
  }
}
```

### `POST /en/economy/workOvertime` — failure shapes (all observed in KB doc)

```json
{ "status": false, "message": "Not enough overtime points" }
{ "status": false, "message": "Not enough energy for overtime" }
{ "status": false, "message": "Overtime not available yet" }
```

When all client-checkable preconditions are clean and we still get `status: false`, treat as employer cap (R4).

## Decision matrix

Inputs at decision time: `jobData.overTime`, `state.completedActions.workOvertime`, `state.overtimeCapReachedAt`, `settings.workOvertime.{enabled, mode}`, `now`.

| Condition | Action | Notes |
|---|---|---|
| `!settings.enabled` | skip | feature off |
| `state.overtimeCapReachedAt != null` | skip | cap was hit today |
| `mode === 'once-per-day'` AND `state.completedActions.workOvertime != null` | skip | already done today |
| `jobData.overTime == null` | skip | not employed |
| `jobData.overTime.nextOverTime > now` | skip (silent) | cooldown — would burn 100 energy |
| `jobData.overTime.points < 24` | skip (silent) | not enough points |
| `jobData.overTime.usableEnergy < 10` | skip (silent) | not enough energy |
| else | POST | proceed |

After POST:

| Response | State mutation | Telegram |
|---|---|---|
| `status: true` | `completedActions.workOvertime = { at: now, source: 'agent' }` (if unset); never set to '`external`' here even in `when-available` mode — agent-initiated | `💼 OT: +{netSalary} {currency}` |
| `status: false` AND preconditions were clean | `overtimeCapReachedAt = now` | `⛔ overtime: employer cap reached…` (one-shot) |
| `status: false` AND preconditions were stale (race) | no mutation; will re-evaluate next cycle | silent |

A "preconditions were clean" check at POST-time is the same as the decision matrix above — we already gated on it before POSTing, so any `status: false` after a clean gate is a cap signal.

## Memory model

Extend `DailyState`:

```ts
const ActionRecord = z.object({ at: z.string(), source: z.enum(['agent', 'external']) });

export const DailyState = z.object({
  // … existing fields …
  completedActions: z.object({
    work: ActionRecord.optional(),
    train: ActionRecord.optional(),
    buyFood: BuyFoodRecord.optional(),
    vipClaim: ActionRecord.optional(),
    workOvertime: ActionRecord.optional(),     // NEW
  }),
  overtimeCapReachedAt: z.string().nullable().default(null),  // NEW
  // … existing fields …
});
```

Day rollover (`loadOrInit` archives `daily-state-{prevDay}.json` and creates a fresh one) clears both fields automatically.

`ACTIVE_SAFE_DAILY_KEYS` is extended to:

```ts
export const ACTIVE_SAFE_DAILY_KEYS = ['work', 'train', 'workOvertime', 'vipClaim', 'buyFood'] as const;
```

The order is significant — `pendingActions(state)` preserves it, and `runAction` is invoked in that order from `runCycle`.

## Open questions / risks

- **Q: What if `overTime` is absent in `job-data` because the citizen is unemployed?** A: `isEmployee: false` means the response lacks `overTime`. The decision matrix entry "`jobData.overTime == null` → skip" covers this. We don't trigger `autoEmploy` from the OT path — that responsibility stays with the `work` action.
- **Q: Race condition between reconcile and POST.** A: reconcile reads `nextOverTime > now` at the start of the cycle. The POST happens later in the same cycle. If reconcile fired (marking `workOvertime` external), the once-per-day path skips. The `when-available` path proceeds — but the cooldown check before POST catches it (`nextOverTime > now` → skip). Safe.
- **Risk: Other failure shapes than the documented three.** If the employer goes bankrupt mid-day or the player gets fired, POST returns `status: false`. R4 treats all clean-precondition failures the same way (pause until day rollover) — which is the right policy even if the cause isn't literally "cap reached".
- **Risk: Telegram spam in `when-available` mode for high-points players.** A player with thousands of points could trigger ~12-24 OTs per day at 1-per-cooldown. Each emits one Telegram message. This is intentional — the operator opted into the mode. If it proves noisy, a future change can debounce digests.
